## ✨ امکانات

### مدیریت تجهیزات
- **ثبت جامع دستگاه و قطعات** با تمام فیلدها (نوع، برند، مدل، سریال، پارت‌نامبر، مشخصات فنی، و …)
- **تاریخ خروج از انبار** و **تاریخ تحویل به مشتری** (ورودی شمسی با تقویم پاپ‌آپ، ذخیره‌ی شمسی+میلادی)
- **وضعیت دستگاه:** فعال | معیوب | در حال تعویض | تعویض‌شده
- **علت تعویض:** سخت‌افزار / نرم‌افزار / سایر + شرح توضیحات
- **گرید جدولی قطعات (جدید):** افزودن چند قطعه به‌صورت اکسل‌مانند با Paste چندردیفی، تکمیل خودکار (autocomplete) پارت‌نامبر و هشدار قرمز سریال تکراری در همان لحظه

### کاتالوگ قطعات (جدید)
- **مرجع واحد پارت‌نامبرها:** جدول `part_catalog` هر پارت‌نامبر را یک‌بار تعریف می‌کند (PN1، PN2، عنوان، مشخصات فنی)
- **Sync خودکار:** ویرایش مرجع، عنوان/مشخصات/پارت‌نامبرهای **همه‌ی قطعات متصل** را هم‌زمان به‌روز می‌کند؛ **ادغام (Merge)** دو مرجع با انتقال قطعات
- **Autocomplete هوشمند:** در فرم قطعه، تعویض گارانتی و گرید جدولی — با انتخاب مرجع، عنوان و مشخصات و PN2 خودکار پر می‌شوند
- **ثبت و آپدیت دستی:** دکمه‌ی «＋ مرجع جدید» برای تعریف مرجع از صفر + ویرایش کامل هر مرجع (با sync خودکار قطعات وصل)
- **قالب اکسل قابل دانلود (جدید):** از دیالوگ آپدیت — شیت «کاتالوگ» با ۴ ستون و ردیف‌های نمونه + شیت «راهنما»ی فارسی؛ همان فایل مستقیماً قابل بارگذاری در import است (چرخه‌ی کامل قالب ↔ import)
- **آپدیت گروهی از اکسل/Paste (جدید):** دو قالب پذیرفته می‌شود — ردیف‌محور سرستون‌دار (پارت‌نامبر، عنوان قطعه، مشخصات فنی، پارت‌نامبر ۲) یا فهرست انبار (ردیف ۱ عنوان، ردیف ۲ توضیح، ردیف ۳ پارت‌نامبر)؛ پیش‌نمایش خشک قبل از ثبت؛ رفتار upsert: مرجع جدید ساخته و فیلدهای پرشده‌ی فایل در مرجع موجود اعمال می‌شوند — هیچ رکوردی حذف نمی‌شود
- **اصلاح و ادغام (جدید/فیکس):** ویرایش PN اشتباه مرجع (PUT) پارت‌نامبر همه‌ی قطعات وصل را هم اصلاح می‌کند؛ ادغام مراجع تکراری/اشتباه قطعات همه را به مرجع درست منتقل می‌کند (باگ endpoint ادغام فیکس شد)؛ «sync دستی» قطعات بی‌مرجع را وصل می‌کند
- مدیریت کاتالوگ از منوی **لیست‌ها ← 🧩 کاتالوگ قطعات**

### یکتایی و جست‌وجوی سریال (جدید)
- **ایندکس یکتای سراسری:** ثبت سریال تکراری در POST/PUT/PATCH و batch با خطای **۴۰۹** رد می‌شود؛ در ورود اکسل/Paste با «skip + دلیل»
- **جست‌وجوی فوری سریال** در فهرست قطعات (debounce، کوئری `?serial=`) + بج «تکراری ⚠» + دیالوگ «صاحبان سریال» با لینک به همه‌ی نسخه‌های قطعه، تجهیز و پروژه
- چک سریال از سمت کلاینت: `POST /api/parts/serial-check` با آرایه‌ی matches

### جست‌وجوی پیشرفته (جدید)
- **جست‌وجوی سراسری در هدر برنامه** روی پروژه‌ها، تجهیزات، قطعات، کارشناسان و تعویض‌ها
- فیلتر نوع (`types=`)، صفحه‌بندی، شمارش هر نوع (`type_counts`) و رتبه‌بندی تطبیق پارت‌نامبر (کامل > پیشوند > جزئی)

### گارانتی
- **مدت گارانتی** (ماه) + **تاریخ شروع گارانتی** → محاسبه‌ی خودکار پایان گارانتی
- **درخواست‌های گارانتی:** در انتظار | تأیید | رد | انجام‌شده
- **تعویض قطعه تحت گارانتی:** جریان مرحله‌ای (انتخاب پروژه ← دستگاه ← قطعه‌ی خراب ← قطعه‌ی جدید)
- **ردیابی زنجیره‌ای:** مسیر کامل قطعه از فروش تا تمام تعویض‌ها

### تأمین قطعات
- **منبع تأمین:** داخلی / خارجی
- **تاریخ خرید** + **مدت گارانتی تأمین‌کننده** + یادداشت

### ورود سریال‌ها از اکسل و Paste
- **آپلود مقصددار:** ابتدا **پروژه** و **تجهیز مقصد** انتخاب می‌شود — آپلود بدون مقصد پذیرفته نمی‌شود و هم‌خوانی پروژه/تجهیز در سرور اعتبارسنجی می‌شود
- **تب «چسباندن لیست»:** بدون فایل — کپی از اکسل و Paste در textarea با همان قالب و پیش‌نمایش قبل از ثبت
- **🧩 پیشنهاد مرجع کاتالوگ:** پارت‌نامبرهای ناشناس با «عنوان قطعه» و «مشخصات/توضیحات» ردیف‌های فایل در پیش‌نمایش به‌عنوان مرجع کاتالوگ پیشنهاد می‌شوند و با ثبت (چک‌باکس فعال — پیش‌فرض) ساخته می‌شوند تا همه‌ی قطعات هم‌پارت‌نامبر آینده اطلاعات یکسان بگیرند (پارامتر `create_catalog`)
- قالب «فهرست قطعات انبار»: **ردیف ۱** عنوان قطعه | **ردیف ۲** مدل/توضیحات | **ردیف ۳** پارت‌نامبر | **ردیف ۴ به بعد** سریال‌ها
- تطبیق سه‌مرحله‌ای پارت‌نامبر: ۱) قطعات دستگاه مقصد ۲) کل سامانه ۳) پارت‌نامبر خودِ دستگاه (→ به‌روزرسانی `main_serial`)
- **قطعه‌ی ناشناخته = ساخت خودکار:** اگر پارت‌نامبر در سامانه نباشد، قطعه‌ی جدید با عنوان ردیف ۱ + توضیحات ردیف ۲ + پارت‌نامبر ردیف ۳ روی دستگاه مقصد ساخته می‌شود
- سریال مازاد در هر ستون (چند عدد از یک قطعه) ← قطعه‌ی جدید جداگانه
- گزارش کامل پس از عملیات: تطبیق‌ها، قطعات جدید، سریال‌های به‌روز، پارت‌نامبرهای بدون تطبیق
- فقط مدیر؛ اجرای مجدد امن (idempotent)؛ هیچ داده‌ای حذف نمی‌شود

### گزارش‌ها و داشبورد
- کارت‌های آماری (تعداد تجهیزات، قطعات، تعویض‌ها، پروژه‌ها)
- آخرین تعویض‌های گارانتی + لیست پروژه‌ها
- پرخرابی‌ترین قطعات، خرابی بر اساس مشتری/دلیل، نیاز خدمات به تفکیک نوع
- نمای مشتری: تجهیزات، قطعات و سابقه‌ی خدمات یک پروژه

### مدیریت لیست‌ها
- کارشناسان فروش/فنی، برندها، انواع و مدل‌های دستگاه، پروژه‌ها، دلایل خرابی

## 🐳 اجرا با Docker (توصیه‌شده)

کل سامانه (API + فرانت‌اند) در **یک کانتینر** روی پورت 4000 سرو می‌شود.
دیتابیس SQLite در volume به نام `app-data` نگهداری می‌شود و با rebuild از بین نمی‌رود.

### ۱) تنظیم متغیرهای محیطی

```bash
cp .env.example .env
# سپس JWT_SECRET و رمزهای کاربران را در .env ویرایش کنید
```

> متغیرهای لایسنس (`LICENSE_ENFORCE`، `TRIAL_DEVICE_LIMIT`، `TRIAL_LIMIT_ENFORCE`) هم در `.env.example` مستند شده‌اند — در نسخه‌ی فعلی هر سه خاموش‌اند (رایگان، بدون محدودیت).

### ۲) ساخت و اجرا

```bash
docker compose up -d --build
```

سپس مرورگر را باز کنید: **http://localhost:4000**

**حساب‌های پیش‌فرض:**
| نقش | نام کاربری | رمز عبور |
|------|-----------|----------|
| مدیر (Admin) | `admin` | `admin123` |
| کاربر (User) | `user` | `user123` |

### ۴) فعال‌سازی با کد لایسنس (پس از خرید)

بعد از خرید یکی از طرح‌های بالا، کد فعال‌سازی (JWT امضاشده با RSA) دریافت می‌کنید. مدیر سامانه از منوی **🔑 ورود کد لایسنس** کد را وارد می‌کند:

1. «بررسی کد» → امضا با کلید عمومی داخل سرور تأیید و طرح/دارنده نمایش داده می‌شود (بدون اینترنت)
2. «🔓 فعال‌سازی» → طرح، دارنده و تاریخ پایان اعمال و سقف تجهیزات برداشته می‌شود
3. هر کد فقط یک‌بار قابل استفاده است؛ سوابق فعال‌سازی در همان صفحه دیده می‌شود
4. **تست پیش از انتشار (smoke)**: `node scripts/smoke-test.mjs --issue` کل چرخه‌ی کد لایسنس را خودکار
   تست می‌کند — صدور واقعی با ابزار فروشنده + تأیید امضای محلی + بررسی/فعال‌سازی/replay/جعلی/ابطال
   (کلید خصوصی محلی لازم است؛ روی سرور تست با `BASE=...` هم اجرا می‌شود)
5. **ابطال کد (ادمین)**: برای استرداد خرید یا سرقت کد، شناسه‌ی کد (jti) یا خودِ کد را در بخش
   «⛔ ابطال کد لایسنس» وارد کنید — کد باطل‌شده در آن سامانه فعال نمی‌شود (403)؛ ابطال با
   «لغو ابطال» برگشت‌پذیر است. فرآیند فروشنده: [docs/sales-guide.md](docs/sales-guide.md)

کدها **آفلاین** اعتبارسنجی می‌شوند؛ هیچ اطلاعاتی به بیرون ارسال نمی‌شود.

> 🛒 فرآیند صدور کد برای فروشندگان (فاکتور تا ارسال): [docs/sales-guide.md](docs/sales-guide.md)

### ۶) به‌روزرسانی image در Docker Hub

نام image در `docker-compose.yml` روی `meysam8498/support-equipment-management:latest` تنظیم است؛
پس از هر تغییر:

```bash
docker compose build
docker tag meysam8498/support-equipment-management:latest meysam8498/support-equipment-management:1.20.1
docker push meysam8498/support-equipment-management:latest
docker push meysam8498/support-equipment-management:1.20.1
```

> توضیحات کامل image (Overview فارسی) در [`DOCKER_HUB_OVERVIEW.md`](DOCKER_HUB_OVERVIEW.md) نگهداری می‌شود.

### ۷) انتشار خودکار با GitHub Actions

با push کردن تگ ورژن، image به‌صورت خودکار بیلد و روی Docker Hub منتشر می‌شود:

```bash
git tag v1.2.2
git push origin v1.2.2
```

- تریگرهای دیگر: انتشار **Release** در گیت‌هاب و اجرای دستی (تب Actions ← Run workflow).
- تگ‌های ساخته‌شده از `v1.2.1`: **1.2.1**، **1.2**، **1** و **latest**.
- پیش‌نیاز یک‌باره: دو Secret در تنظیمات ریپو (Settings ← Secrets and variables ← Actions):
  `DOCKERHUB_USERNAME=meysam8498` و `DOCKERHUB_TOKEN` (Access Token با دسترسی Read/Write از
  hub.docker.com ← Account Settings ← Security).
- نسخه‌ی OCI LABEL داخل image هم از تگ گیت پر می‌شود (`ARG APP_VERSION`).
- فایل workflow: [`.github/workflows/docker-publish.yml`](.github/workflows/docker-publish.yml)

### ۸) یادآور همگام‌سازی مستندات و نسخه‌ها

ورژن و مستندات نباید از هم جا بمانند؛ سه لایه‌ی چک خودکار وجود دارد:

| لایه | فایل | کِی اجرا می‌شود |
|------|------|----------------|
| اسکریپت چک | `scripts/check-docs-sync.mjs` | دستی: `node scripts/check-docs-sync.mjs` |
| هوک pre-commit | `.githooks/pre-commit` | قبل از هر کامیت محلی (نیازمند فعال‌سازی یک‌باره: `git config core.hooksPath .githooks`) |
| CI گیت‌هاب | `.github/workflows/docs-check.yml` | هر push/PR + گام مشابه قبل از پابلیش داکر |

چک سازگاری است، نه اجبار محتوا: کامیت‌های عادی (کد/فیکس بدون تغییر نسخه) آزادند؛ فقط اگر ورژن‌ها با هم یا با مستندات ناهماهنگ شوند، کامیت/CI رد می‌شود.
رد موقت برای موارد خاص: `git commit --no-verify`.

آن‌چه بررسی می‌شود: ورژن هر سه `package.json` (+lock)، بج «نسخه‌ی فعلی» و ردیف تاریخچه در README، بج نسخه‌ی image و جدول تگ‌ها و تاریخچه در DOCKER_HUB_OVERVIEW، هدر و `ARG APP_VERSION` داکرفایل و هدر compose و namespace هاب.

برای انجام همه‌ی این کارها با یک دستور، اسکریپت `bump-version` وجود دارد:

```bash
node scripts/bump-version.mjs 1.3.0 --commit --tag --hub
```

- ورژن را در همه‌ی ۸ نقطه به‌روز می‌کند (سه package.json + lock، بج‌های README و Overview، جدول تگ‌ها، داکرفایل و compose) و ردیف تاریخچه‌ی جدید را درج می‌کند؛
- ردیف‌های جدید با شرح جای‌نویز («… را اینجا بنویسید») درج می‌شوند — شرح واقعی را بنویسید و دوباره با همان فلگ‌ها اجرا کنید تا کامیت/تگ/هاب انجام شود؛
- چک همگام‌سازی در پایان اجرا می‌شود و اگر قرمز یا جای‌نویز مانده باشد، کامیت/تگ انجام نمی‌شود (exit=2)؛
- `--commit` کامیت موضوعی می‌سازد، `--tag` تگ `vX.Y.Z` محلی می‌سازد و `--hub` Overview هاب را با توکن credential store همگام می‌کند (توکن فقط در حافظه)؛
- پابلیش خودکار image با push کردن تگ راه می‌افتد: `git push origin v1.3.0`.

## 📥 ورود سریال‌ها از فایل اکسل

در منو (فقط مدیر): **ورود سریال از اکسل** — یا API مستقیم:

```bash
# آپلود مقصددار با curl — project_id و device_id الزامی است
TOKEN=...   # توکن مدیر
curl -X POST http://localhost:4000/api/serial-import \
     -H "Authorization: Bearer $TOKEN" \
     -F "file=@فهرست-قطعات.xlsx" \
     -F "project_id=1" \
     -F "device_id=2"
```

**قالب فایل** (مطابق نمونه‌ی «چهار دستگاه سرور دیوان محاسبات»):

| ردیف | محتوا | مثال |
|------|-------|------|
| ۱ | عنوان قطعه در هر ستون | Case، Main Board، Power، … |
| ۲ | مدل/توضیحات (اختیاری) | HPE DL380 Gen10 |
| ۳ | پارت‌نامبر هر قطعه (کلید تطبیق) | P19928-001 |
| ۴ به بعد | سریال‌ها — هر ردیف = یک دستگاه | PXLANACLMJ22AK |

نکات:
- **مقصد الزامی است:** بدون `project_id` و `device_id`، آپلود خطا برمی‌گرداند؛ و اگر تجهیز به پروژه‌ی انتخابی تعلق نداشته باشد هم رد می‌شود.
- ستون A فقط شماره‌ی ردیف است و نادیده گرفته می‌شود.
- تطبیق سه‌مرحله‌ای: اول قطعات دستگاه مقصد، بعد کل سامانه، و اگر پارت‌نامبر مال خودِ دستگاه باشد → `main_serial` به‌روز می‌شود.
- **پارت‌نامبر ناشناخته → ساخت قطعه‌ی جدید:** عنوان از ردیف ۱، توضیحات از ردیف ۲، پارت‌نامبر از ردیف ۳، سریال از همان سلول.
- اگر در یک ستون سریالِ بیشتری از قطعات ثبت‌شده باشد، قطعه‌ی جدید دیگری ساخته می‌شود.
- هیچ داده‌ای حذف نمی‌شود؛ اجرای دوباره‌ی همان فایل امن است.
- پس از عملیات، گزارش کامل (تطبیق‌ها، قطعات جدید، پارت‌نامبرهای بدون تطبیق) نمایش داده می‌شود.

## 🔑 ساختار پروژه

```
Support/
├─ server/                     # بک‌اند: Node.js + Express + TypeScript
│  └─ src/
│     ├─ db/                   # اسکیمای SQLite، راه‌انداز و seed
│     ├─ routes/               # API: auth, devices, parts, warranty, lists,
│     │                        #      warrantyRequests, procurement, serialImport,
│     │                        #      users, dashboard, reports
│     ├─ middleware/            # احراز هویت و کنترل نقش (requireRole)
│     └─ lib/                  # تبدیل تاریخ شمسی/میلادی، رمز و توکن
├─ client/                     # فرانت‌اند: React 18 + Vite + TypeScript + Tailwind CSS
│  └─ src/
│     ├─ pages/                # صفحه‌ها (داشبورد، تجهیزات، قطعات، گارانتی، گزارش‌ها، لیست‌ها، ورود اکسل، کاربران)
│     ├─ components/           # JalaliDatePicker, StatusBadge, Modal, Layout, SelectField
│     ├─ context/              # ThemeContext (دارک/لات), AuthContext (کاربر + نقش)
│     ├─ api/api.ts            # کلاینت API با انواع TypeScript
│     └─ i18n/fa.ts            # برچسب‌های فارسی
├─ Dockerfile                  # Multi-stage build (builder + runtime)
├─ docker-compose.yml
├─ .env.example
└─ README.md
```

### مدل داده (خلاصه)

- **users** — نقش (`admin` | `user`) + ایمیل + فعال/غیرفعال
- **devices** — تجهیزات با وضعیت، تاریخ انبار/تحویل، گارانتی، علت تعویض
- **parts** — قطعات با زنجیره‌ی جایگزینی (`replaces_part_id`)
- **warranty_replacements** — تاریخچه‌ی تعویض
- **warranty_requests** — درخواست‌های گارانتی
- **procurement** — تأمین قطعات (داخلی/خارجی)

هر تاریخ هم شمسی (`*_jalali`) و هم میلادی (`*_gregorian`) ذخیره می‌شود.

**مهاجرت خودکار:** اگر دیتابیس با نسخه‌ی قدیمی اسکیما ساخته شده باشد، در اولین اجرا ستون‌های جاافتاده
(وضعیت، گارانتی، پارت‌نامبرها و…) بدون از دست رفتن داده‌ها اضافه می‌شوند (`migrateSchema`).

## 🛡️ امنیت

- رمزهای عبور با `bcrypt` هش می‌شوند
- نشست با توکن JWT و انقضای زمانی
- کاربر غیرفعال (`active=0`) نمی‌تواند وارد شود
- middleware `requireRole('admin')` برای محدودسازی نوشتن
- ورود سریال از اکسل فقط برای مدیر؛ **مقصد (پروژه+تجهیز) الزامی و اعتبارسنجی‌شده**؛ محدودیت حجم فایل (۱۰MB)
- اعتبارسنجی ورودی‌ها با `zod`
- فایل دیتابیس و `.env` در گیت نادیده گرفته می‌شوند
